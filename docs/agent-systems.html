CASE STUDY 02 / MCP / AUTONOMY BOUNDARIES

Ein Agent entscheidet.
Ein System kontrolliert.

Aus einer echten KI-Werkzeugentscheidung wurde ein reproduzierbarer GitHub-Actions-Lauf mit realen MCP-Calls – ohne dem Modell unbegrenzte Ausführungsrechte zu geben.

Repository und Nachweise ↗Technische Fragen stellen
Auftrag

Android-Research-Readiness prüfen, ohne ein APK, Endgerät oder reales Kundensystem anzufassen. Ziel war nicht ein spektakulärer Sicherheitsfund, sondern der technisch kontrollierte Übergang von Agentenentscheidung zu echter Toolausführung.

33Validierungschecks im belegten GitHub-Workflow
229im damaligen MCP-Katalog sichtbar; nicht 229 ausgeführt
ARCHITEKTUR / SOURCE FIRST

Vom Toolvorschlag zum erlaubten Aufruf

  1. 01 · PLANCamber wählt drei read-only Tools
  2. 02 · VALIDATEfeste Allowlist, leere Argumente, maximal 3 Calls
  3. 03 · EXECUTEGitHub Actions startet REA MCP und führt tools/call aus
  4. 04 · VERIFYToolantworten, Fehler und Grenzen getrennt prüfen

Die Toolauswahl wurde in der Camber-Agentenlaufzeit beobachtet. Ein separater Actions-Runner startete anschließend tatsächlich die REA-Serverkommunikation und führte binary_session, inspect_apktool_client und inspect_adb_client innerhalb fester Argument- und Mengenlimits aus. Die Tests blockierten unter anderem unbekannte Tools, mehr Calls und Zielpfade.

33 Checks, drei MCP-Aufrufe

Die datierte Workflow-Abnahme dokumentiert reale Toolantworten, nicht nur einen bestandenen JSON-Schema-Test.

Die originalen Toolauswahl- und Planartefakte sind verknüpft. Ein Workflow-Lauf ist nicht mit einer neuen autonomen Camber-Sitzung gleichzusetzen.

Agenten-Entscheidung und Akzeptanz ↗
SECURITY BOUNDARY

Allowlist statt freier Toolwahl

Ausführung benötigt eine vorgeprüfte Tool-ID, leere Argumente und begrenzte Zahl an Aufrufen. Der Runner akzeptiert keine beliebigen Modellbefehle.

Die GitHub-Schedule kann den REA-Executor starten, aber nicht automatisch beweisen, dass Camber eine neue Modellplanung ausgelöst hat. Ebenso keine tatsächliche APK-Analyse.

Diese Arbeit zeigt eine wiederverwendbare Integrationsidee: Ein LLM plant, eine deterministische Berechtigungsschicht prüft, die Ausführungsumgebung ruft zugelassene Tools auf und ein unabhängiger Test unterscheidet Erfolg, Abstention und Umgebungsprobleme.

Keine erfundene Produktivwirkung
